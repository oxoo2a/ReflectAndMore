# Stage 07: generating classes at run time

## Pain in stage 06

Two limits remained. Dynamic proxies (stage 04) can only implement interfaces, so a class
without an interface cannot be intercepted. And run-time compilation (stage 05) needs source
code and a compiler, which is slow and unavailable on a plain JRE. Frameworks need neither:
they write class files directly.

## Mechanism

The ClassFile API (`java.lang.classfile`, standard since Java 24) reads and writes class
files. A generated byte array becomes a class through `ClassLoader.defineClass` or, for a
hidden class, through `MethodHandles.Lookup.defineHiddenClass`. The JVM does not care where
the bytes came from.

`Main` walks through:

1. reading the bytecode of `Candidate.f` with the ClassFile API, like `javap -c`
2. writing a complete `Capability` implementation from nothing, annotation included, and
   verifying, defining and using it
3. a generated subclass of `Candidate` that intercepts `getX` and `f`: the class proxy
   that stage 04 could not provide
4. hidden classes, the mechanism behind lambdas
5. writing the generated classes to disk for `javap`
6. the whole spectrum from annotation processors to native image

## New files

| File | Purpose |
|---|---|
| `Bytecode.java` | parses class files and lists methods and instructions |
| `Generator.java` | builds the implementation class and the intercepting subclass instruction by instruction |
| `ByteArrayClassLoader.java` | exposes `defineClass` |
| `Interceptor.java` | the static hook the generated subclass calls |

`Candidate` is unchanged. The container of stage 06 was dropped; the annotation types and
`Dependency` stay because `Candidate` refers to them.

## In the real world

- `java.lang.reflect.Proxy` (stage 04) and `LambdaMetafactory` (stage 01) generate classes
  exactly like section 2, inside the JDK.
- CGLIB, ByteBuddy and Javassist generate subclasses as in section 3 for Spring class proxies,
  Hibernate lazy entities, Mockito mocks and Jakarta CDI scoped beans.
- Before Java 24 all of them used the ASM library; the JDK itself is moving to the ClassFile API.
- Annotation processors (Lombok, MapStruct, Dagger) do the same work at compile time, and
  GraalVM native image forbids it at run time altogether.

## Cost

- Writing bytecode by hand is error-prone; the verifier catches structural mistakes, not
  logical ones. Frameworks keep this code small and well tested.
- Generated classes complicate debugging and stack traces (`Candidate$$Intercepted`,
  `$$EnhancerBySpringCGLIB$$`), and they are invisible to static analysis.
- Each generated class costs metaspace; hidden classes help because they are unloaded with
  their last instance.
- None of this works in a closed-world ahead-of-time build.

## Exercises

1. Extend `Generator.interceptingSubclass` so that the generated method also reports the
   return value of `getX` to `Interceptor` (hint: `dup` before `invokestatic`).
2. Generate the subclass for any class and any list of public non-final methods, with the
   method list taken from reflection. Compare the result with stage 04's `LoggingHandler`.
3. Measure a call through the generated subclass against a call through a stage 04 dynamic
   proxy and against a direct call.
4. Remove `-d 2` or swap two instructions in `Generator` on purpose and look at what
   `ClassFile.verify` and the JVM report.
